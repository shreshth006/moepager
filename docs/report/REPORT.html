1. Title, Abstract and Architecture

1.1 Abstract

Mixture-of-Experts (MoE) language models activate only a few "expert" sub-networks per layer for each token: 8 of 64 in OLMoE-1B-7B, 4 of 32 in gpt-oss-20b, 8 of 128 in Qwen3-30B-A3B. That makes them attractive for consumer machines, which run them with llama.cpp in mmap mode when the model is larger than free RAM, leaving the Linux page cache to decide which weights stay in memory.

We show that the kernel's generic behaviour fits this workload poorly:

  • Scattered units. One expert's weights are three slices in three tensors hundreds of megabytes apart.
  • Read-around pollution. On a page fault, the kernel reads a window around the faulting page: 4 MiB on our test machine's btrfs. That pulls unused neighbouring experts into the cache and multiplies SSD traffic 3.7–4.8×.
  • Repacking. llama.cpp's default CPU weight repacking moves 77–100 % of expert bytes into anonymous memory, outside the page cache.

We present moepager, a Rust toolchain and an unprivileged user-space daemon that manage the shared page cache at the granularity of (layer, expert) units, without changing the inference engine's code or binary:

  1. It parses the GGUF header into an exact expert map.
  2. It observes expert misses black-box by polling sentinel pages with mincore().
  3. It answers each miss with expert-completion readahead: bulk posix_fadvise(WILLNEED) of the expert's remaining slices in 128 KiB chunks. The chunking is necessary because the kernel silently truncates larger requests.
  4. A 64-line LD_PRELOAD shim turns off fault read-around on the model mapping, which no stock llama.cpp option does on single-node machines.

The evaluation toolchain records ground-truth routing from llama.cpp, computes exact LRU miss-ratio curves, simulates policies against a Belady optimum, and runs llama.cpp under cgroup memory limits.

On a 15 GB laptop running OLMoE-1B-7B (4.2 GB) under memory limits of 1.5 GB and 2.5 GB, moepager's configuration decoded 1.40 and 3.21 tokens/s, versus 0.35 and 0.87 tokens/s for the same engine served by the default page cache. That is 3.7–4.0× faster, with 7–8× less SSD traffic and memory-pressure stall reduced from 12.7 % to 1.0 %. Default llama.cpp, by contrast, was OOM-killed at both limits unless allowed to spill 2.3–2.5 GB into compressed RAM swap. On a second model, gpt-oss-20b (12.1 GB), replaying real routing under 4 GB and 6 GB limits showed the same pattern: 1.6–2.0× faster than the kernel default, with 3–4× less data read.

We also report what did not work: a value-based pinning policy captured little of the optimal policy's 34–74 % miss reduction, and completion readahead without turning off read-around made performance worse.

1.2 System architecture

moepager is a user-space control loop around the Linux page cache. It sits beside an unmodified inference engine, observes the engine only through the page cache they share, and acts only through standard kernel interfaces. 1.2.1 Architectural style

  • Layered, with ports and adapters. Policy code is pure: it consumes observations and emits Action values, and never calls the kernel. All operating-system effects sit behind two traits (PageCacheOps, ResidencyProbe), with a Linux implementation and a mock one. This lets the same policy run in the simulator, in tests and in the daemon.
  • One core, two hosts. The policy crate mp-core is linked both into the trace-driven simulator (mp-sim) and into the live daemon (moepagerd), so a policy evaluated offline is exactly the policy deployed (ADR 0001).
  • Three planes.
    • An offline plane runs once per model file: it parses the header and builds the expert map.
    • An online plane is the observe → decide → act loop of the daemon.
    • An evaluation plane records ground truth, simulates policies against an optimal bound, and benchmarks under memory limits.
  • Non-invasive. Nothing in the engine's source or binary is changed. The only intervention in the engine's process is an optional LD_PRELOAD shim that adds one madvise call after mmap.

/// mp-sim: policy hooks driven by the simulator (StaticPin, VControl, ...).
pub trait Controller {
    fn on_access(&mut self, layer: u16, expert: u16, unit: u32, hit: bool, t_ns: u64);

  • In the simulator, controllers that model black-box observation must drop the hit = true calls themselves, which is how the miss-only regime is evaluated.
  • External interfaces: the GGUF file format [2]; the kernel system calls and /proc files listed under mp-os [3]; cgroup v2 control files [4]; the .mpt trace format (docs/TRACE_FORMAT.md); the expert map as JSON (map.json).

1.2.5 Runtime data flow

For each decoded token, with the recommended configuration (engine with -nr and the shim; daemon with --policy v --budget-mb 0):

  1. The engine computes layer l and reads the k experts the router chose. Pages of the chosen units that are not resident cause page faults. Because of MADV_RANDOM, each fault reads only the faulting page.
  2. The faulted page is inserted into the shared page cache. If it is a sentinel, the unit's sentinel flips from non-resident to resident.
  3. Within one poll period (300 µs in the experiments), SentinelSource reports the flip as an ExpertEvent for (l, e).
  4. moepagerd updates OnlineStats and infers token boundaries from the layer order.
  5. The prefetcher returns Action::Prefetch(u). LinuxOps issues posix_fadvise(WILLNEED) for every slice of u in 128 KiB chunks, and the kernel starts large asynchronous reads.
  6. The engine's remaining faults on u are satisfied by pages that are already resident or already under I/O. They wait on the in-flight read instead of issuing their own small reads.
  7. If a pin budget is set, every 4 tokens the residency planner may emit Pin / Unpin / Demote actions, which become mlock / munlock / process_madvise(MADV_COLD).
  8. Under the cgroup's memory.max, the kernel's reclaim (MGLRU [5]) evicts unpinned pages as usual; the daemon never evicts by itself unless demotion is enabled.

Offline, mp-gguf produces the map used in steps 2–5. For evaluation, moe_trace replaces steps 2–3 with exact router output, and mp-sim replaces steps 1, 6 and 8 with a model of the cache and the I/O device.

  • No copies. Both processes map the same file, so they share the same page-cache folios. A page the daemon prefetches or pins is the page the engine reads.
  • One memory budget. Both run in one cgroup v2 scope with a memory.max limit [4]. Page-cache pages are charged to the cgroup of the task that brought them in, so co-location makes the daemon's prefetches count against the same budget as the engine's faults (ADR 0008). The daemon warns when it is not in the engine's cgroup.
  • Start-up checks (--pid): the engine's mapping must carry the rr (random-read) VmFlag in /proc/<pid>/smaps, otherwise read-around is still on; the memlock limit is compared with the pin budget.
  • Failure isolation. If the daemon stops, the engine continues with plain kernel behaviour; every action is a hint, and pins are released when the daemon's mapping is closed.

2. Introduction and Problem Statement

2.1 Background

Mixture-of-Experts (MoE) language models [6, 7] replace each dense feed-forward block with many smaller "expert" networks plus a router. For every token, the router picks a few experts per layer (top-k), so only a small fraction of the parameters is used per token. In the three models studied here, OLMoE [8], gpt-oss [9] and Qwen3 [10] (values read from the real model file headers [11]):

Model File (quantisation) Size Layers × experts top-k Expert share of file
OLMoE-1B-7B-0924 Q4_K_M 4.21 GB 16 × 64 8 92.6 %
gpt-oss-20b MXFP4 12.11 GB 24 × 32 4 84.1 %
Qwen3-30B-A3B Q4_K_M 18.56 GB 48 × 128 8 94.6 %

Because only 4–8 experts per layer are touched per token, MoE models are an attractive fit for consumer machines. A common way to run a model larger than free RAM is llama.cpp [1] in mmap mode: the model file is mapped into memory, and the Linux page cache loads weights on demand and evicts them under memory pressure.

2.2 Problem statement

The kernel's page cache is generic. Its reclaim policy (MGLRU [5]) and its fault read-around [12] know nothing about how a GGUF file [2] is laid out or how MoE routing behaves. Our measurements on a 15 GB laptop (Section 6) show three concrete problems:

  1. The unit of use is scattered. One expert at one layer is stored as three slices in three different tensors (ffn_up_exps, ffn_gate_exps, ffn_down_exps), hundreds of megabytes apart. The kernel cannot know these three ranges belong together.
  2. Read-around pollutes the cache. On a page fault, Linux reads a window around the faulting page: 4 MiB on this machine's btrfs filesystem. For expert slices of about 1–1.3 MB, most of that window belongs to neighbouring experts that will not be used. Replaying real OLMoE routing under a 1.5 GB budget, the SSD read 1.80 GB per token to deliver 0.49 GB of needed expert weights (3.7× amplification), and almost every expert access missed.
  3. Fault-driven reads are slow. Faulting cold experts in through mmap delivered only 0.15–0.24 GB/s on the real model file. Reading the same bytes with large prefetch requests delivered 1.5–1.7 GB/s.

A further, practical problem: llama.cpp on x86 CPUs with AVX2 by default repacks the most common quantised expert weights into ordinary (anonymous) memory. That is 77 % of the expert bytes for OLMoE and Qwen3 Q4_K_M, and 100 % for gpt-oss MXFP4. Under memory pressure those pages go to swap instead of the page cache.

Goal: make MoE inference faster on memory-constrained Linux machines, using knowledge of the model file's structure and of routing behaviour, without modifying the inference engine and without copying the weights.

3. Literature Review and Objectives

3.1 Related work

MoE offloading inside the inference engine. Most systems that keep only part of an MoE model in fast memory are built into the engine, where the router's decisions are directly visible:

  • mixtral-offloading (Eliseev and Mazur [13]): LRU expert cache plus speculative prefetch.
  • MoE-Infinity (Xue et al. [14]): activation-aware expert cache.
  • HOBBIT (Tang et al. [15]): mixed-precision experts, implemented as about 8,000 lines added to llama.cpp.
  • Pre-gated MoE [16], DuoServe-MoE [17] and similar systems: predict next-layer experts and prefetch them. Liu et al. [18] survey this design space.

Inside llama.cpp itself there are several open proposals [19]: PR #25294 (O_DIRECT expert streaming that bypasses the page cache), PR #26824 (expert heat map and mmap pinning), PR #29887, issue #20757 and discussion #27149. All of these modify the engine.

Using the OS page cache as the expert tier. Si et al. [20] is the closest study. On a datacenter GH200 node they show that kernel recency (LRU) serves about as much demand as an oracle static-frequency pin, that Belady's bound [21] leaves about one third of LRU's misses addressable, and that fadvise(WILLNEED) prefetch hints gained only 0.3–5 %. Their engine reads with pread, so mmap fault behaviour and file structure play no role.

Operating-system mechanisms.

  • cache_ext / cachebpf (Zussman et al. [22]) lets eBPF programs replace page-cache eviction, but needs a patched kernel.
  • MGLRU [5] and DAMON [23] are generic and know nothing of model structure.
  • vmtouch [24] pins or evicts file ranges given by the user.
  • "LLM in a flash" (Alizadeh et al. [25]) bundles co-used weights so that flash reads are large. That is the same idea as our expert-completion readahead, but it is implemented inside the engine and requires reformatting the model. PowerInfer [26] similarly exploits activation locality inside the engine, keeping frequently activated ("hot") neurons in fast memory.

Gap. We found no system that manages the page cache for an unmodified engine using the model file's structure, and none that measures the effect of mmap fault read-around on MoE experts.

3.2 Objectives

  • O1. Build an exact map from GGUF files to (layer, expert) units and their byte and page ranges, verified on real models.
  • O2. Observe expert usage from outside the engine, without root.
  • O3. Build an evaluation toolchain: ground-truth routing traces, trace analysis, a policy simulator with an optimal (Belady) bound, real-kernel replay, and benchmarks under a fixed memory budget.
  • O4. Implement page-cache actuators: chunked readahead, pinning and demotion. Combine them in a daemon whose policy code is identical to the simulated one.
  • O5. Decide go/no-go on real hardware with predefined kill criteria, and report only measured numbers.

4. Methodology and Algorithms

This section defines the problem formally (4.1), then describes each algorithm in the order data flows through the system: the expert map (4.2), black-box observation (4.3), read-around suppression (4.4), expert-completion readahead (4.5), the optional residency policy (4.6) and the offline evaluation algorithms (4.7). 4.1 Problem model and notation

Symbol Meaning

L, E, k number of MoE layers, experts per layer, experts chosen per token per layer (top-k)

t_f fixed cost of one demand miss (fault entry plus first I/O latency)

Decoding token t touches, layer by layer, every unit in R_{t,l} plus the dense (non-expert) tensors of layer l. The engine maps F read-only and shared, so every touched byte is served from the page cache, which holds at most C bytes (minus the engine's anonymous memory). A unit access is a hit if all its pages are resident and a miss otherwise.

The quantity to minimise is decode time per token. Under memory pressure it is dominated by I/O stall, which a simple cost model captures:

    stall(miss of u)  =  t_f + s_u / B_d               (kernel default)
    stall(miss of u)  =  t_f + t_detect + s_u / B_b     (with completion readahead)

Two levers follow directly. Residency (which units stay cached) reduces the number of misses. Read path (how a missing unit is read) reduces the cost of each one. The original hypothesis was that residency is the main lever; Section 6 shows that on an mmap engine the read path dominates, because B_d is small and the kernel's read-around inflates the bytes read per miss.

4.2 Expert map from the GGUF header (mp-gguf)

A GGUF file [2] starts with a header listing every tensor's name, shape, ggml type and data offset. mp-gguf parses only this header, so a truncated prefix of the file is enough. For each tensor named blk.<l>.ffn_{up,gate,down,gate_up}_exps.weight with shape [ne0, ne1, E], the expert index is the outermost (slowest-varying) dimension, so each expert's weights are contiguous inside the tensor:

Algorithm 1  BuildExpertMap(header)
  for each tensor T matching blk.<l>.ffn_*_exps.*:
      bytes  := type_size(T.type) * (ne0 * ne1 * E) / block_size(T.type)
      stride := bytes / E                       # warn if E does not divide bytes
      for e in 0 .. E-1:
          add slice [T.offset + e*stride, T.offset + (e+1)*stride) to unit (l, e)
  for each 2-D per-expert tensor ([ne0, E], e.g. *_exps.bias):
      add one row per expert to unit (l, e)
  sort all slices by offset; build page->unit interval index (below)
  for each slice: choose a sentinel page (Section 4.3)
  • Page → unit index. Slices are 32-byte aligned rather than page aligned, so a boundary page can belong to two units. The index stores slices as intervals sorted by start, plus a prefix-maximum array of interval ends, so the owners of any page are found by binary search in O(log n + r), where r ≤ 2 is the number of owners.
  • Repacking check. mp-gguf also reports which expert tensors llama.cpp's CPU backend would repack into anonymous memory, based on the quantisation type and the repack rules in the engine source [1]. On AVX2 this covers 77 % (Q4_K_M) to 100 % (MXFP4) of the expert bytes, so the engine must run with --repack 0 / -nr for the weights to stay in the page cache.
  • Cost. O(number of tensors) to parse, O(n log n) to sort the n slices (n = 3·L·E; 3,072 for OLMoE, 18,432 for Qwen3-30B-A3B).
  • Verification. Fixture GGUF files with known layouts are checked slice by slice (kind, offset, length of every unit), the page index is checked against the slices, and the real headers of OLMoE-1B-7B [8], gpt-oss-20b [9] and Qwen3-30B-A3B [10] are checked for layer, expert and top-k counts and unit sizes.

4.3 Black-box observation by sentinel pages (mp-recorder)

The engine is a black box: the daemon cannot see router decisions. It infers them from the page cache, which is shared.

Sentinel choice. For each slice, one page in its middle is chosen as the sentinel, at least 128 KiB (SENTINEL_GUARD) from either edge of the slice. A fault in a neighbouring slice brings in a read-around window around the faulting page; with the default 128 KiB window, that window cannot reach this sentinel. Slices shorter than 2 × 128 KiB + 2P are marked unreliable, and bias rows (a few KiB, inside other tensors' pages) get no sentinel. On btrfs the window is 4 MiB, larger than a whole OLMoE slice, which is why read-around must be turned off (Section 4.4) for observation to be correct as well as fast.

Polling. The daemon maps F read-only (MAP_SHARED, PROT_READ) and calls mincore(2) [3] on the sentinel pages. This needs no privilege and works for files the daemon does not own. (cachestat(2) would need write access to the file.)

Algorithm 2  SentinelTick(sentinels, prev, now_ns)       # every Δ = 300 µs
  events := []
  for i, s in enumerate(sentinels):
      r := mincore(s.page)
      if r and not prev[i] and (s.layer, s.expert) not in events:
          events.append((now_ns, s.layer, s.expert))      # a miss of unit (l, e)
      prev[i] := r
  return events
  • Semantics. A sentinel changing from non-resident to resident means "unit (l, e) has just been faulted in", which is a miss. Hits are invisible: pages already mapped are read through the CPU's page tables without entering the kernel, so no user-space interface reports them. All online statistics are therefore miss-only (ADR 0002).
  • Cost. One mincore call per sentinel per sweep: O(3·L·E) system calls every Δ. The poll period Δ bounds detection latency to at most Δ plus the remaining sweep time.
  • False positives. A sentinel can also turn resident because of the daemon's own prefetch of the same unit, or because read-around from an unrelated fault reached it. The first case is harmless (it re-issues a prefetch for a unit being read anyway). The second is eliminated by turning read-around off.
  • Privileged alternative. With root, the same events can be taken exactly from the filemap:mm_filemap_add_to_page_cache tracepoint; a bpftrace script is included (ADR 0009). It was not used for the results.

Token boundaries are not visible either. Within one decode step layers are visited in increasing order, so a new token is inferred when an event's layer falls more than a slack (default 2 layers) below the highest layer seen in the current step:

Algorithm 3  InferToken(event)                             # ADR 0010
  if max_layer is set and event.layer + slack < max_layer:
      end_token()                       # closes statistics, may trigger re-plan
  max_layer := max(max_layer, event.layer)

The slack absorbs reordering when several layers are discovered in the same sweep. On ground-truth traces this recovers the true token count; on miss-only traces a token whose misses are all in high layers can merge with the previous one, which only affects the V(e) rate estimates.

4.4 Read-around suppression (tools/preload)

On a page fault in a file mapping, Linux reads a window of pages around the faulting address ("read-around"), sized from the backing device's read_ahead_kb (4 MiB for this machine's btrfs). For a 1–1.3 MB expert slice, most of that window is neighbouring experts that will not be used. The waste has two effects: up to 3.7–4.8× more SSD traffic than needed, and a cache filled with unused pages, which raises the miss ratio.

Setting MADV_RANDOM on the mapping (VM_RAND_READ in the kernel) disables read-around for it, so a fault reads exactly the faulting page. Stock llama.cpp applies this only when --numa is set on a multi-node machine. A 64-line LD_PRELOAD shim wraps mmap() and, for read-only shared mappings of *.gguf files, calls madvise(addr, len, MADV_RANDOM) after the original mmap returns (ADR 0011). The engine's code and binary are unchanged. The daemon verifies the effect by checking for the rr flag in the engine's /proc/<pid>/smaps VmFlags and warns if it is missing.

Turning read-around off alone trades one problem for another: each miss becomes hundreds of synchronous 4 KiB faults (39,000 per token in Experiment B). Completion readahead (next section) turns them back into bulk reads, but only for the unit that was actually chosen.

4.5 Expert-completion readahead (moepagerd, mp-os)

When a miss of unit u is observed, the daemon immediately asks the kernel to read all of u asynchronously. The engine is typically still inside the first slice (up); the gate and down slices, hundreds of megabytes away in the file, arrive as large reads instead of thousands of small faults.

Algorithm 4  OnMiss(u)                                     # mp-core::prefetch
  for each slice [a, b) in S(u):
      for c in a, a+128K, a+256K, ... < b:                  # chunked (ADR 0006)
          posix_fadvise(fd, c, min(128K, b - c), POSIX_FADV_WILLNEED)
  stats.observe(u, MISS)
  • Chunking. A single WILLNEED is silently truncated by force_page_cache_ra() in mm/readahead.c [12] to max(io_pages, ra_pages) pages, so a 1 MiB request populated only 256 KiB in our tests. Issuing 128 KiB chunks makes every byte requested actually read.
  • Asynchrony. WILLNEED queues reads and returns, so the daemon never blocks on I/O. The alternative MADV_POPULATE_READ (--prefetch-mode populate) is synchronous and runs on a worker thread; it is for devices where readahead is disabled and WILLNEED has no effect.
  • Prediction-free. The action is taken only for units the router has already chosen, so it never wastes bandwidth on wrong guesses. A cross-layer predictive variant (--predict) exists but is not recommended (Section 6).
  • Repeated misses. Each unit has three sentinels, so one real miss can trigger up to three prefetches of the unit. A refractory window that suppressed repeats within 20 ms was evaluated and doubled misses (Phase 7 ablation: decode speed fell from 5.4 to 2.1 tok/s), because the repeats re-fetch pages reclaimed while the engine is still working through the unit. The window is therefore off by default.
  • Cost. O(s_u / 128 KiB) system calls per miss, about 30 for an OLMoE unit; no data is copied, and the pages are shared with the engine.
  • Memory accounting. Pages read on the daemon's behalf are charged to the daemon's cgroup. Daemon and engine are therefore run in the same cgroup (ADR 0008), so prefetching cannot exceed the budget C.

4.6 Residency policy V(e) (mp-core; optional, needs privilege)

With CAP_IPC_LOCK (or a raised RLIMIT_MEMLOCK), the daemon can pin units with mlock through its own shared mapping, which pins the same page-cache folios the engine reads. The policy chooses a pinned set within a pin budget C_pin ≤ C by value per byte:

    V(u) = rate(u) · (t_f + s_u / B_d) / s_u

that is, the expected stall avoided per token per byte held. This is a fractional-knapsack relaxation; the greedy order is optimal for the relaxation and near-optimal when units are small compared with C_pin.

Rate estimator under miss-only observation. A pinned unit produces no misses, so naive miss counts would make every pinned unit look cold. rate(u) is instead defined as the miss rate per token while unpinned:

    rate(u) = (Σ_t w_t · miss_t(u) + p·k) / (Σ_{t: u unpinned at t} w_t + k)
  • w_t = g^t with g = 2^{1/h} is an exponential decay weight with half-life h = 64 tokens, implemented by growing the weight of new events instead of shrinking old ones (O(1) per event, renormalised when w exceeds 10^100).
  • p is a prior rate and k = 0.05·w_t a light shrinkage, so a unit exposed for one token is not estimated at exactly 0 or 1.
  • While a unit is pinned its estimate is frozen. At each re-plan a random 2 % of pinned units are released ("exploration") so frozen estimates are refreshed.
Algorithm 5  Replan(stats, cost)                  # every 4 tokens (replan_every)
  excluded := random 2 % of pinned units          # exploration, miss-only only
  cand := [(V(u) * (1.25 if pinned[u] else 1), u) for u not excluded, V(u) > 0]
  sort cand by value descending                   # hysteresis factor 1.25
  want := {}; used := 0
  for (v, u) in cand:
      if used + s_u <= C_pin: want += u; used += s_u
  emit Unpin(u) [+ Demote(u)] for u pinned and not in want     # unpins first,
  emit Pin(u) for u in want and not pinned                     # so C_pin holds
  • Cost. O(n log n) per re-plan for n = L·E units (1,024 for OLMoE), amortised over 4 tokens.
  • Hysteresis. A pinned unit's value is multiplied by 1.25 when ranking, so a newcomer must beat it by 25 % to displace it. This bounds pin/unpin churn.
  • Demotion. Units that leave the pinned set can be marked cold with process_madvise(pidfd, MADV_COLD) on the engine's mapping (needs CAP_SYS_NICE). posix_fadvise(DONTNEED) was rejected because it does not drop pages that another process has mapped (verified on Linux 6.19; ADR 0003).

The policy code is one Rust implementation used by both the simulator and the daemon (ADR 0001), so simulated and live behaviour cannot drift apart.

4.7 Offline evaluation algorithms (mp-sim, mp-analyze)

Trace-driven simulation. mp-sim replays a trace σ against a cache of C bytes:

  • a hit costs nothing;
  • a miss is queued on a single FIFO I/O channel and costs t_f + s/B_d, or t_f + t_detect + s/B_b with completion readahead;
  • compute time per layer is taken from the trace timestamps;
  • the reported quantities are miss ratio, bytes read, and modelled stall.

Policies compared: LRU (a stand-in for the kernel's MGLRU [5]), LFU, prefix pinning, an oracle static-frequency pin, V(e) with full or miss-only observation, predictive prefetch, and Belady*.

Belady* evicts the cached unit whose next use is furthest in the future [21]. For equal sizes this is optimal (MIN). With variable sizes exact optimality is NP-hard, so the same rule is used as the standard heuristic and labelled with an asterisk. Implementation: for each unit, the sorted list of its positions in σ; the next use after position i is found by binary search; cached units are kept in an ordered set keyed by next use, so each access costs O(log N).

Exact LRU miss-ratio curve. mp-analyze computes, independently of the simulator, the miss ratio of a byte-capacity LRU cache at every capacity in one pass, using stack-distance analysis [27] with a Fenwick tree [28]:

Algorithm 6  ByteReuseDistances(σ)
  fenwick := zeros(N)                      # one slot per trace position
  for i, u in enumerate(σ):
      if last[u] exists:
          D_i := fenwick.sum(last[u]+1 .. i-1)   # bytes of distinct units since last use
          fenwick.add(last[u], -s_u)
      else:
          D_i := infinity                        # cold miss
      fenwick.add(i, +s_u); last[u] := i
  # access i hits in LRU of capacity C  <=>  D_i + s_u <= C
  MRC(C) := |{ i : D_i + s_u > C }| / N         # sort thresholds once, O(N log N)

Each position holds the size of the unit whose latest access is there, so a range sum counts each distinct unit once. The whole curve costs O(N log N). The simulator's LRU agrees with this curve exactly at every tested capacity; this cross-check between two independent implementations is a regression test.

4.8 Experimental protocol

Hypotheses and kill criteria. The project was run as a go/no-go experiment (ADR 0004) with criteria fixed before measuring (IDEA_REVIEW §6):

  • K1: Belady* cannot save at least 15 % of misses relative to LRU at any realistic capacity → residency management is pointless.
  • K2: fault-driven bandwidth is at least 0.75× bulk bandwidth → the read path is not worth changing.
  • K3: default llama.cpp beats every page-cache configuration at equal memory → the approach has no user.

4.10 Threats to validity

  • Internal.
    • A desktop session ran during the measurements; background activity adds noise, visible as run-to-run spread in some D configurations.
    • B uses one replay per variant; D uses 3 repetitions of 32 tokens. Differences below about 10 % should not be read as significant.
    • /home is btrfs with zstd compression, so device bytes can be lower than logical bytes. Quantised weights compress poorly, and the comparisons are between configurations on the same file.
    • Per-process I/O counters (/proc/self/io) do not include reads issued by another process. B's traffic is therefore taken from the cgroup (4.9); an earlier draft used the replayer's own counter and understated the daemon variants by 0.1–0.6 GB/token.
    • B0's swap device is zram, which is RAM. Its "fast" result uses memory outside the 1.5 / 2.5 GB budget, so it is reported separately.
  • Construct.
    • The replay tool (B) touches pages but does not compute; it measures paging, not inference. D measures the real engine.
    • LRU in the simulator is an approximation of MGLRU [5]; B shows the kernel's behaviour directly.
    • Belady* with variable sizes is a heuristic bound, not a proven optimum.
  • External.
    • One machine, one SSD, one filesystem. Read-around on ext4 defaults to 128 KiB, so the pollution effect, and the benefit of turning it off, will be smaller there.
    • End-to-end results exist for OLMoE only. gpt-oss-20b has A–C results; its D run was stopped because the B0 configuration exhausted system memory. Qwen3-30B-A3B was mapped from its header only.
    • Only llama.cpp's CPU backend was studied.
  • Conclusion. The go/no-go decision depends on K1–K3 as defined before measuring; the unanticipated read-around finding is reported as such rather than folded into the original hypothesis.

The repeats re-fetch pages reclaimed while the engine is still working through an expert. The window is therefore off by default.

6.6 Second model: gpt-oss-20b (experiments A–C)

The same pipeline was run on gpt-oss-20b MXFP4: 12.1 GB file, 24 layers × 32 experts, top-4, 13.25 MB per expert unit. Memory limits were 4 GB and 6 GB, and routing was recorded for 3 prompts × 128 tokens. Raw data: bench/results/phase7-gptoss/.

Experiment D did not run. Its first configuration, default llama.cpp, repacks 100 % of gpt-oss's expert bytes (≈ 10 GB) into anonymous memory and swaps them to zram, which lives in RAM. The machine ran critically low on memory and the run was stopped. This is itself evidence of the problem moepager avoids, but there are no end-to-end gpt-oss numbers.

  • Routing (A): 40–47 % token-to-token reuse, next-layer recall 0.54–0.62 versus 0.39–0.46 for popularity. Belady* saves 44–67 % of LRU's misses at 15–50 % capacity, similar to OLMoE.

Reading:

  • The best configuration is the same as for OLMoE: read-around off plus completion readahead, 1.6× and 2.0× faster than the kernel default, with 3–4× less data read (0.31 vs 1.33 and 0.11 vs 0.36 GB/token).
  • Two differences from OLMoE:
    • gpt-oss's expert slices (4.4 MB) are about as large as the read-around window, so read-around wastes less (≈ 1.05× at 4 GB).
    • Read-around off alone is slower than the default here, because 4 KiB faults replace useful large reads.
  • moepagerd turns those small faults back into bulk reads, and also helps somewhat on its own with read-around on (1.06× and 1.22×).

6.7 Comparison with expected outcomes and with existing methods

Expectation (IDEA_REVIEW, before measuring) Outcome
Smarter eviction/pinning is the main lever (≥ 15 % fewer misses possible, K1) The gap exists (Belady* saves 34–74 % vs LRU), but our online V(e) policy did not capture it reliably, and pinning needs privileges. Not the main lever.
Bulk readahead beats fault-driven reads (K2) Confirmed: ≈ 7× (Exp. C).
Default llama.cpp is beaten (K3) Only at equal memory, where it OOMs. With zram it is faster. Partially.
(not anticipated) Fault read-around pollution is the dominant cost: 3.7–4.8× read amplification. Turning it off is required for both correctness of black-box detection and speed.

Relation to existing methods:

  • Si et al. [20] found that fadvise lookahead hints gain ≤ 5 % on a GH200 with a pread-based engine. Our result differs because on an mmap-based engine the problem is how missing experts are read (small synchronous faults plus large wasted read-around), not which experts to keep. Completion readahead attacks exactly that.
  • In-engine systems (MoE-Infinity [14], HOBBIT [15], llama.cpp PR #25294 [19]) see router decisions directly and can avoid the issue entirely. moepager reaches a 3.7–4.0× improvement over the stock page-cache path without modifying the engine's code or binary, at the cost of one LD_PRELOAD hint.

6.8 Go / no-go decision

GO, with narrowed scope (recorded in PHASES.md):

  • The product is "read-around off + expert-completion readahead", validated end to end.
  • V(e) pinning and predictive prefetch are demoted to research options.
  • The next phase must validate on a second machine with disk swap and ext4, and on a larger model.

7. Conclusion

7.1 Summary

We built moepager, a toolchain and daemon that manages the Linux page cache for Mixture-of-Experts inference using the model file's structure, without changing the inference engine's code.

The project was run as an experiment with kill criteria fixed in advance. On a real model (OLMoE-1B-7B) on a 15 GB laptop, the outcome was:

  • Go on the mechanism, no-go on the original emphasis. We expected smarter eviction to be the main lever. Measurement showed the dominant cost under memory pressure is the kernel's fault read-around. On this machine's btrfs it read 3.7× more data than needed and filled the cache with unused neighbouring experts.

  • What works:

    • turning read-around off for the model mapping, with a 64-line LD_PRELOAD shim, since no stock llama.cpp option does this on single-node machines;
    • plus moepagerd's expert-completion readahead in 128 KiB chunks.

    Together they turn tens of thousands of 4 KiB faults per token into bulk reads. See Section 6.5 for the end-to-end numbers. - What doesn't (yet): - Completion readahead without turning read-around off made things worse. - Our V(e) pinning policy only matched LFU when allowed to pin most of the cache. With black-box (miss-only) observation it still loses 10–40 % in most cells, up to 2×, and it needs extra privileges. - Default llama.cpp is faster than every page-cache configuration if it may spill 2.3–2.5 GB of repacked weights into zram (compressed RAM). Without swap it is OOM-killed at both budgets. - Smaller findings with independent value: - The kernel silently truncates WILLNEED. - llama.cpp's default repacking moves 77–100 % of expert bytes out of the page cache. - llama.cpp's --lazy-mode keeps weights in anonymous memory. - btrfs reports different device numbers in stat() and /proc/pid/maps.

7.2 Limitations

  • One machine, one filesystem (btrfs with a 4 MiB readahead window). End-to-end llama.cpp numbers exist only for OLMoE. gpt-oss-20b was evaluated with real routing, replay and the bandwidth benchmark, but its llama-bench run was stopped for low system memory. Qwen3-30B was only mapped from its header.
  • Short runs (32 decode tokens × 3 repetitions in llama-bench); some configurations show large run-to-run spread.
  • A desktop session was running during measurements.
  • Pinning (mlock), demotion (MADV_COLD) and eBPF observation are implemented but untested, because they need privileges.
  • The shim is still an intervention in the engine's process, although it doesn't change its code or binary.

7.3 Future work

  1. Upstream: propose a llama.cpp option to apply MADV_RANDOM to expert tensors on single-node machines, which would remove the need for the shim.
  2. Repeat on ext4 (128 KiB readahead) and on the larger models, with longer runs.
  3. Evaluate pinning end to end with CAP_IPC_LOCK and a pin budget near 90 % of the expert cache. Narrow the miss-only gap with privileged hit observation (DAMON [23]) where available.
  4. Add a fallback when WILLNEED is ineffective (MADV_POPULATE_READ), and PSI-driven [29] control of the memory budget to protect other applications.
